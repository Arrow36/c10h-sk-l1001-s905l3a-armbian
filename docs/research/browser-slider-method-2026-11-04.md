## 1. 一句话概括这次方法创新

**把原本需要反复通过 SSH 输入命令的屏幕测试，改造成 Windows 浏览器里的实时滑杆控制台：由操作者盯着 C10H 的实体 LCD，一边拖动参数，一边即时观察，再把有意义的现象转成针对性验证。**

这种“浏览器控制 + SSH 安全隧道 + 直接写 framebuffer + 人眼实时观察”的组合，不是新发明的底层显示技术，但在本项目里属于**研究流程的创新**。它大幅降低了开展连续观察、颜色通道对照和定位实验的操作门槛；目前没有实测的时间节省比例，不能宣称具体加速倍数。

## 2. 为什么需要改变研究方式

在改用浏览器之前，我们已通过 SSH 完成：驱动绑定、DRM 模式和 Canvas 检查、OSD/Blend/VPP 寄存器读取、ENCL 内部硬件彩条测试等。但普通 Linux 图像仍然表现为**大片不随内容变化的紫色区域，另一侧图像重复、闪动**。

传统工作流程每换一个测试位置、颜色或画面，都要编辑/执行命令、等待结果、重新观察，且用户需要在实体屏幕和 SSH 终端之间频繁切换。这适合读取静态参数，不适合快速观察颜色置换与图案移动的响应规律。

因此我们改变实验粒度：暂时不碰高风险 VPU、OSD、DSI 寄存器，先做**低风险、可重复、即时可见的 framebuffer 像素刺激实验**。

## 3. 技术架构：浏览器并不直接连接屏幕硬件

```text
Windows 电脑                             创维 C10H（fnOS）
┌─────────────────────┐                ┌───────────────────────────────┐
│ 浏览器              │                │ Python 诊断服务               │
│ http://127.0.0.1:8765│  HTTP/JSON    │ 仅监听 127.0.0.1:8765         │
│ 滑杆 / 模式选择      ├─ SSH 隧道 ────►│ /set、/ping、/stop            │
└─────────────────────┘                │          │                    │
                                     │  mmap 写 /dev/fb0            │
 操作者肉眼观察 ◄──── 设备实体屏幕 ◄────┤  可选写 sysfs 背光亮度       │
                                     └───────────────────────────────┘
```

- **浏览器前端**：HTML / JavaScript 滑杆与模式切换；通过请求发送设置值，而不是在 Windows 本地修改画面。
- **C10H 端服务**：Python `ThreadingHTTPServer`，收到控制指令后更新 800×1280 的测试图并写入 `/dev/fb0`；使用 `mmap(MAP_SHARED)` 映射帧缓冲。
- **连接方式**：SSH 本地端口转发 `-L 8765:127.0.0.1:8765`；服务器只监听 C10H 的 loopback 地址，不主动向局域网开放控制端口。
- **硬件显示**：原有 Linux DRM/OSD/ENCL/DSI/面板链路负责把 `/dev/fb0` 的像素显示出来；软件并未绕过这条链路。
- **人参与闭环**：浏览器里指定一个输入 → 肉眼观察实体 LCD → 记录实际输出 → 用下一项有区别度的输入验证假设。

这里的“实时”指交互式快速反馈，**不代表对硬件寄存器进行连续无缝调谐，也没有量化端到端延迟**。

## 4. 三次迭代，从滑杆到故障定位

### 4.1 第一版：位置 / 颜色 / 背光滑杆

文件：`c10h_live_slider.py`

功能：控制测试方块的 X/Y 坐标、R/G/B 数值、背光亮度。图像由程序重新绘制，页面不需要刷新。这样可以快速观察白块移动是否映射到正确区域、颜色是否按预期变化。

核心限制：**仅修改测试图像像素和背光亮度**，不修改 DRM 模式、不修改 OSD/VPP/DSI 寄存器，也不能直接修复画面错位。

### 4.2 第二版：加入 RGB 循环补偿开关

文件：`c10h_live_slider_rgb_test.py`

通过单独拖动 R、G、B，用户发现以下可重复关系：

| 浏览器要求的颜色 | LCD 实际显示 |
|---|---|
| 红 | 绿 |
| 绿 | 蓝 |
| 蓝 | 红 |

为把观察转变成**可验证的假设**，程序加入“标准模式 / 循环错位补偿”切换：

```python
# 小端 XRGB8888 的常规内存字节顺序
pixel = bytes((b, g, r, 0))

# 本次实验验证有效的反向通道排列，仅针对测试图
pixel = bytes((r, b, g, 0))
```

用户确认：**“循环错位补偿后颜色准了。”** 同时系统报告 `/dev/fb0` 颜色位偏移为：

```text
fb0 channel offsets R=16:8 G=8:8 B=0:8
```

**意义**：我们不再只知道“有偏色”，而是确认了一种具体的、可被软件逆置换补偿的**RGB 通道循环映射**。但这还不能证明错误由哪一个硬件模块或寄存器造成，更不能认定全系统颜色已经修复。

### 4.3 第三版：加入全屏纯色模式

文件：`c10h_fullscreen_color_probe.py`

用户反馈开启补偿后，**左侧大片紫色始终不变，右侧仍重复并闪动**。为了区分“颜色交换”和“图像内容根本没传到某些区域”这两类故障，增加：

- 参考图模式：彩条、边框、十字和可移动方块。
- 全屏纯色模式：整张 framebuffer 写成指定 RGB 颜色，可在浏览器里选择纯白、纯黑等。
- 通道补偿模式在两种图案下均可切换。

实际观察：**全屏纯白时，左侧仍为紫色；右侧变成纯白，另有少数像素在闪动。** 这说明普通 framebuffer 更新至少能影响屏幕的一部分，但另一大片区域没有按照当前测试像素变化；纯白的 R/G/B 相等，也说明单纯交换 RGB 通道不足以解释左侧紫色。

> 注意：这是屏幕观察的直接证据，不足以断言损坏发生在 DMA、OSD、VPP、ENCL、DSI 中的哪一段。少量闪动也可能来自控制台并发绘制。

## 5. 浏览器实验如何带动了后续精确检查

浏览器负责**快速改变输入**，而 SSH 负责**精确读取结果**。全屏纯白出现左右不一致之后，我们不再继续盲目调色，而是读取 `/dev/fb0` 内容，验证“CPU 看到的图像是否真的变白”。

**九点抽样**：在不同 X/Y 位置读取，全部返回 `ff ff ff 00`（白）。

**全帧检查**：读取 4,096,000 字节（800×1280×4），原始脚本给出的结果：

```text
读取字节: 4096000
总像素: 1024000
纯白像素: 1023872
非纯白像素: 128
第一个异常位置: x=96 y=288 值=00000000
```

DRM 仍显示 `fb=43`、`XR24`、`pitch=3200`、DMA 地址 `DMA_ADDR`；之前的 Canvas 读数也指向同一地址、相同行跨度和高度。

**已经得到的结论**：CPU 可读取的画面几乎全部为纯白，实体 LCD 却仍有大片紫色。由此应重点审查 framebuffer 在被显示硬件扫描之后的读取、缓存同步、后处理或传输过程。

**测量口径保留**：原脚本用 `data.count(b'\xff\xff\xff\x00')` 统计，未显式按每四字节步进计数；“128 个非白像素”应视为该脚本报告，必要时用逐像素口径复核。即使内存全白，也不等于已经证实 DMA 所见数据正确。

## 6. 比逐条 SSH 操作快在哪里？

| 以往的命令式测试 | 本次浏览器式测试 |
|---|---|
| 每换颜色或坐标需输入/修改命令 | 拖动滑杆，即时提交新值 |
| 很难连续观察红、绿、蓝的变化规律 | 可以快速切换单通道颜色并直接发现循环映射 |
| 临时切换测试图需要改脚本 | 通过模式选择在参考图、全屏纯色间切换 |
| 输入与观察分离，记录较琐碎 | 同一个操作者可连续控制、观察并即时描述 |
| 故障描述较模糊：“花屏、偏色” | 得到结构化现象：“颜色循环错位”“左侧不响应全白” |

**本次效率收益主要来自减少重复操作、提高实验的可比性和快速形成假设。** 尚未记录实验耗时对照，因此不声称节省了多少分钟或提高了多少倍速度。

## 7. 实际使用方式（供以后复现）

以下以最后一版程序为例。已验证的测试环境是 Windows 电脑通过 SSH 连接 C10H，C10H 的 `/dev/fb0` 为 800×1280、32bpp、stride 3200；旧的测试服务应先退出。

**① Windows PowerShell 上传文件**

```powershell
scp "$env:USERPROFILE\Downloads\c10h_fullscreen_color_probe.py" test-user@C10H_IP:/tmp/
```

**② Windows PowerShell 启动远端服务并建立 SSH 隧道**

```powershell
ssh -t -L 8765:127.0.0.1:8765 test-user@C10H_IP "sudo python3 /tmp/c10h_fullscreen_color_probe.py"
```

**③ Windows 浏览器打开**：`http://127.0.0.1:8765`

端口转发、启动及测试均依赖当前 SSH 地址及网络可达性；上例 `C10H_IP` 是当时的实验地址，不保证以后不变。PowerShell 若短暂出现 `channel 3: open failed: connect failed: Connection refused`，可能是网页请求早于远端服务启动；本次随后记录的 `GET / HTTP/1.1 200` 表明服务确实正常接收了浏览器访问。

**④ 结束测试**：网页点击“结束测试，恢复原画面”，或在服务终端按 `Ctrl+C`。程序会尝试恢复之前缓存的 framebuffer 内容及原始背光值。恢复是**尽力而为**，进程异常崩溃、内核卡死或其他控制台同时写入时不保证结果。

本次使用过的脚本均可在历史对话文件中找到：

```text
c10h_live_slider.py
c10h_live_slider_rgb_test.py
c10h_fullscreen_color_probe.py
```

## 8. 设计细节与安全边界

根据实际脚本核对：

| 机制 | 实际做法 | 目的 |
|---|---|---|
| 服务绑定 | `127.0.0.1:8765` | 不直接向局域网暴露 HTTP 控制台 |
| 传输保护 | SSH `-L` 端口转发 | 通过 SSH 访问远端本地服务 |
| 前端更新 | `input` 后约 90 ms 防抖 | 避免每一微小移动都触发连续重绘 |
| 保活检测 | 浏览器约每 3.5 s 请求 `/ping` | 表示操作界面仍在连接 |
| 断线超时 | 超过 90 s 未收到请求后尝试恢复 | 避免测试图长期覆盖画面 |
| 恢复机制 | 缓存原 `/dev/fb0`，保存背光值 | 正常停止时尽力恢复 |
| 背光范围 | 1 至设备报告的 `max_brightness` | 避免滑杆直接关掉背光 |
| 参数检查 | 要求 800×1280、32bpp、stride 3200；限制范围 | 防止程序在不兼容的 fb0 上误写 |
| 权限 | 通过 `sudo` 运行测试服务 | 允许访问 `/dev/fb0` 与背光 sysfs |
| 硬件范围 | 仅 framebuffer 与可选背光 | 不对 OSD/VPP/DSI/PHY 实行任意寄存器写操作 |

**重要安全事实**：目前该网页并非带用户认证、可公开暴露的远程管理产品；它依赖 SSH 隧道和本地 loopback 进行访问限制。不要修改成监听 `0.0.0.0` 后直接暴露到互联网，也不要在未验证寄存器位定义和回退机制前追加危险的 VPU/DSI“调参滑杆”。

## 9. 方法本身带来的三条研究成果

**成果 A：把“偏色”变成了具体的可验证通道排列。** 标准测试 R→G、G→B、B→R；逆置换后颜色恢复，形成了可供驱动源码排查的线索。

**成果 B：把“花屏”分解为两个不同的故障现象。** 通道补偿后颜色能准，但左侧大块紫色不变、右侧仍重复/闪动，说明不能把全部故障归咎于 RGB 顺序。

**成果 C：用可控输入关联精确内存证据。** 浏览器全白刺激 + SSH 显存读取，证明了“CPU 所见几乎全白、屏幕局部不响应”的矛盾，明确下一轮应该分析的是普通图像扫描与传输链路，而不是继续猜测测试图是否画错。

## 10. 如何继续升级这套研究方法

优先推荐的改进不是增加更多危险滑杆，而是：

1. **实验记录自动化**：每次滑动或切换模式自动记录输入、时间戳和屏幕照片编号，便于复盘。
2. **严格逐像素显存校验**：在进入全屏单色模式后，直接按每 4 字节检查每个像素，记录异常坐标分布；尽可能避免 console 并发绘制。
3. **可重复的阶梯与条纹图**：用简单、明确的测试纹理检查坐标映射、行重复规律、闪动区域；不改硬件寄存器。
4. **下一阶段才考虑硬件控制**：如果找到经过代码核实的 OSD/VPP 单一可变参数，先设置有限离散值、单变量、独立 SSH 恢复程序与超时保护；不要用自由连续滑杆写未知寄存器。

本次研究**没有**解决 C10H 的整屏几何错位，也没有证明具体故障位于哪一个硬件模块；其价值是让我们获得了过去用静态读取难以迅速发现的、可重现的故障规律。

## 可复制接续摘要

> 在创维 C10H（S905L3A / JD9366TC、800×1280）USB 启动的 fnOS `6.12.41-trim` 中，内屏已点亮、ENCL 硬件彩条完整，普通 framebuffer 图像却出现左侧大面积紫色不随画面变化、右侧重复与闪动。为加快诊断，我们在 C10H 上运行了 Python `ThreadingHTTPServer`，通过 Windows 的 SSH 本地端口转发访问 `http://127.0.0.1:8765`，用浏览器滑杆实时调整方块 X/Y、R/G/B、背光，并追加 RGB 循环补偿和全屏纯色模式。控制台仅映射并写 `/dev/fb0` 及可选背光 sysfs，不写 VPU/DSI 寄存器。实测原始颜色 R→G、G→B、B→R，改写像素字节排列 `(R,B,G,0)` 后测试图颜色恢复正确，fb0 仍报告标准 R16/G8/B0。全屏纯白时屏幕右侧变白、左侧紫色不变并伴少量闪动；CPU 读取 `/dev/fb0` 4096000 字节基本全白，原脚本报告 128 个非白单位（统计需按像素步进复核），DRM 报告 fb=43、pitch=3200、DMA=DMA_ADDR，Canvas 也一致。结论：浏览器交互显著降低重复命令操作，使颜色通道问题与空间错位问题得以区分；当前**仅完成诊断，未修好普通图像显示**。
